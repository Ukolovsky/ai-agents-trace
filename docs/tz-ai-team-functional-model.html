ТЗ. Видение и функциональная модель AI-команды по внедрению продуктовых решений

1. Назначение AI-команды

AI-команда обеспечивает полный цикл внедрения AI- и Agentic AI-решений: от получения POC и подтвержденного бизнес-сценария до реализации, интеграции с основным продуктом и формирования стабильной переиспользуемой capability.

AI-команда отвечает за технологическое взросление AI-решений, их архитектуру, интеграцию с основным продуктом, production-реализацию AI-части и формирование необходимых требований к Frontend, Backend, Design и Analytics.

AI-команда не заменяет команды основной разработки и не дублирует Vibe Coding.

2. Место AI-команды в процессе разработки

Процесс разработки AI-решений строится по следующей модели:

Клиент / Бизнес → Vibe Coding → AI-команда → Основная разработка + AI-команда → Production → Capability → Vibe Coding

Vibe Coding

Vibe Coding обеспечивает:

  • быстрое уточнение бизнес-задачи;
  • согласование основных требований с клиентом;
  • создание рабочего POC;
  • проверку бизнес-сценария;
  • получение обратной связи от клиента;
  • фиксацию результата эксперимента.

Результатом этапа является подтвержденный бизнес-сценарий и POC, достаточный для перехода к технологическому проектированию.

AI-команда

AI-команда обеспечивает:

  • анализ POC;
  • разработку целевой архитектуры;
  • проектирование AI/Agentic AI-части;
  • определение границ автономности AI;
  • проектирование интеграции с основным продуктом;
  • формирование TDR;
  • формирование требований к Backend и Frontend;
  • развитие Semantic Layer;
  • определение Governance;
  • разработку Evaluation;
  • выбор технологического решения;
  • разработку AI-кода;
  • интеграцию AI-кода с основным продуктом;
  • доведение AI-решения до production;
  • формирование переиспользуемых capabilities.

Основная разработка

Основная разработка обеспечивает реализацию изменений в core product, необходимых для интеграции AI-решения:

  • Backend;
  • Frontend;
  • Design;
  • Analytics;
  • API;
  • domain logic;
  • data model;
  • product capabilities.

3. Основной принцип ответственности

AI-команда является владельцем AI Solution.

AI-команда самостоятельно реализует и доводит до production:

  • agents;
  • AI services;
  • orchestration;
  • tools;
  • MCP-интеграции;
  • AI APIs;
  • agent state;
  • AI-specific logic;
  • evaluation;
  • governance-механизмы;
  • AI-specific integration layer.

Основная разработка является владельцем core product и самостоятельно реализует изменения внутри основного продукта, необходимые для предоставления AI-команде требуемых product capabilities.

4. Жизненный цикл AI-решения

4.1. Discovery и POC

Vibe Coding:

  1. получает бизнес-задачу;
  2. проводит discovery;
  3. уточняет требования с клиентом;
  4. определяет пользовательский сценарий;
  5. создает POC;
  6. проверяет результат с клиентом;
  7. передает результат AI-команде.

На данном этапе архитектура production-решения не является обязательным результатом.

4.2. AI Solution Analysis

AI-команда анализирует полученный POC и определяет:

  • целевой бизнес-сценарий;
  • роль AI в процессе;
  • необходимость использования AI;
  • тип AI-решения;
  • границы ответственности AI;
  • границы автономности;
  • необходимые инструменты;
  • необходимые данные;
  • необходимые интеграции;
  • существующие product capabilities;
  • отсутствующие product capabilities.

AI-команда определяет целевую модель решения.

5. AI Solution Architecture

AI-команда разрабатывает архитектуру решения, включающую:

  • AI-компоненты;
  • agents;
  • orchestration;
  • tools;
  • MCP;
  • AI services;
  • APIs;
  • data flow;
  • state management;
  • Semantic Layer;
  • Governance;
  • Evaluation;
  • Human-in-the-loop;
  • интеграцию с core product.

Архитектура определяет границы ответственности между AI-командой и командами основной разработки.

6. Проектирование Agentic AI

Для каждого агента AI-команда определяет:

  • назначение;
  • бизнес-сценарий;
  • входные данные;
  • контекст;
  • доступные знания;
  • Semantic Layer;
  • tools;
  • допустимые действия;
  • запрещенные действия;
  • уровень автономности;
  • точки human approval;
  • правила эскалации;
  • состояние;
  • взаимодействие с другими агентами;
  • взаимодействие с пользователем;
  • критерии успешного выполнения;
  • критерии остановки и fallback.

AI-команда определяет, является ли конкретный сценарий:

  • AI Assistant;
  • AI Advice;
  • AI Execution;
  • AI Collaboration;
  • Agent;
  • Multi-Agent Solution;
  • AI Orchestrator;
  • deterministic workflow с AI-компонентами.

7. TDR и интеграция с основным продуктом

TDR является основным артефактом интеграции AI-решения с core product.

AI-команда формирует TDR и определяет:

  • необходимые product capabilities;
  • необходимые API;
  • необходимые backend changes;
  • необходимые frontend changes;
  • необходимые изменения domain model;
  • необходимые данные;
  • необходимые права доступа;
  • необходимые события;
  • необходимые интеграции;
  • границы ответственности систем;
  • контракты взаимодействия;
  • требования к состоянию и результатам AI-операций.

TDR используется для согласования AI-решения с Backend и Frontend-командами.

AI-команда сопровождает TDR до момента согласования необходимых изменений и реализации интеграционных контрактов.

8. Требования к Backend

AI-команда формирует требования к Backend основной разработки, необходимые для реализации AI-сценария.

Требования включают:

  • новые API;
  • расширение существующих API;
  • product capabilities;
  • domain operations;
  • доступ к данным;
  • события;
  • permissions;
  • состояния;
  • бизнес-операции;
  • интеграционные контракты;
  • требования к производительности;
  • требования к безопасности.

Backend-команда реализует изменения внутри core product.

AI-команда обеспечивает соответствие реализованных изменений требованиям AI Solution.

9. Требования к Frontend

AI-команда формирует требования к Frontend основной разработки, необходимые для полноценного пользовательского сценария AI.

Требования включают:

  • точки входа в AI-функциональность;
  • отображение состояния агента;
  • отображение результата;
  • отображение ошибок;
  • approval / confirmation;
  • управление AI-действиями;
  • настройки;
  • пользовательский контроль;
  • отображение статуса выполнения;
  • взаимодействие пользователя с AI.

Frontend-команда реализует изменения внутри core product.

AI-команда обеспечивает соответствие реализации целевому AI-сценарию.

10. Semantic Layer

AI-команда отвечает за развитие Semantic Layer в рамках AI-решений.

Для каждого нового сценария AI-команда определяет:

  • необходимые бизнес-сущности;
  • определения;
  • связи;
  • бизнес-правила;
  • контекст;
  • capabilities;
  • tool contracts;
  • ограничения;
  • дополнительные семантические зависимости.

Новые знания и изменения Semantic Layer становятся частью переиспользуемой AI-инфраструктуры компании.

11. AI Governance

AI-команда определяет Governance для AI-решения.

Governance включает:

  • допустимые действия AI;
  • запрещенные действия;
  • права доступа;
  • доступные tools;
  • ограничения автономности;
  • human approval;
  • правила эскалации;
  • audit trail;
  • logging;
  • контроль изменений;
  • обработку ошибок;
  • контроль использования данных;
  • контроль критических операций.

AI Solution не считается production-ready без определенных механизмов контроля, соответствующих его уровню автономности и риску.

12. AI Validation & Testing

AI-команда отвечает за комплексную валидацию AI/Agentic AI-решения перед его передачей в production. Цель этапа: подтвердить не только техническую работоспособность решения, но и его качество, надёжность, безопасность, производительность и экономическую эффективность.

AI Validation является отдельной инженерной функцией и не сводится к стандартному QA или функциональному тестированию продукта.

12.1. Функции AI Validation

AI-команда должна:

  • формировать стратегию тестирования AI/Agentic AI-решения;
  • определять критерии успешности AI-решения;
  • формировать evaluation datasets и тестовые сценарии;
  • создавать golden datasets / эталонные наборы;
  • проверять качество ответов и выполнения бизнес-задач;
  • проверять корректность выбора и использования tools / MCP;
  • проверять корректность аргументов, передаваемых инструментам;
  • проверять соблюдение бизнес-правил;
  • тестировать edge cases и негативные сценарии;
  • проводить adversarial testing;
  • проверять поведение при неполном, противоречивом или некорректном входе;
  • проверять необходимость и корректность human-in-the-loop;
  • проводить regression testing при изменении модели, промптов, tools, orchestration или Semantic Layer;
  • оценивать latency, throughput и стабильность;
  • проводить нагрузочное и стресс-тестирование AI-компонентов;
  • оценивать token consumption и стоимость выполнения;
  • проверять устойчивость к сбоям моделей, tools и внешних сервисов;
  • проверять AI Governance и ограничения автономности;
  • фиксировать результаты тестирования и ограничения решения;
  • определять готовность решения к production engineering.

12.2. Объекты тестирования

Тестироваться должен не только финальный ответ LLM, а весь AI execution flow:

User Input → Context → Agent/Orchestrator → Reasoning → Tool Selection → Tool Execution → Business Operation → Final Result

В зависимости от решения оцениваются:

  • качество понимания задачи;
  • корректность reasoning / planning;
  • корректность выбора агента или workflow;
  • корректность выбора инструмента;
  • корректность параметров tool call;
  • соблюдение Semantic Layer и бизнес-контекста;
  • соблюдение бизнес-правил;
  • корректность результата;
  • необходимость эскалации человеку;
  • безопасность выполнения;
  • устойчивость к ошибкам;
  • latency;
  • стоимость;
  • воспроизводимость и стабильность поведения.

12.3. Типы AI Evaluation

AI-команда должна применять комбинацию различных методов оценки:

Functional Evaluation

  • выполнение целевой задачи;
  • корректность результата;
  • соответствие acceptance criteria.

Tool / Agent Evaluation

  • выбор правильного tool;
  • корректность tool arguments;
  • правильность последовательности действий;
  • корректность agent trajectory;
  • корректность orchestration.

Business Evaluation

  • соблюдение бизнес-правил;
  • корректность работы с бизнес-сущностями;
  • выполнение бизнес-процесса;
  • достижение требуемого business outcome.

LLM Evaluation

  • качество генерации;
  • factuality;
  • relevance;
  • consistency;
  • structured output;
  • использование LLM-as-a-Judge там, где это оправдано.

Safety & Governance Evaluation

  • попытки выполнить запрещённые действия;
  • обход ограничений;
  • prompt injection;
  • excessive agency;
  • privilege escalation;
  • утечка данных;
  • нарушение permission model;
  • корректность human approval.

Performance Evaluation

  • latency;
  • throughput;
  • concurrency;
  • error rate;
  • resource consumption;
  • деградация качества под нагрузкой.

Economic Evaluation

  • token consumption;
  • стоимость одного execution;
  • стоимость пользовательской операции;
  • стоимость при целевой нагрузке;
  • сравнение моделей и архитектурных вариантов.

12.4. Evaluation Dataset

Для значимых AI-решений должен формироваться отдельный набор тестовых сценариев, включающий:

  • типовые успешные сценарии;
  • edge cases;
  • негативные сценарии;
  • неоднозначные запросы;
  • неполные данные;
  • противоречивые данные;
  • запрещённые действия;
  • сценарии с human approval;
  • сценарии ошибок tools и внешних систем;
  • реальные обезличенные пользовательские сценарии, если это допустимо;
  • синтетические сценарии для покрытия редких случаев.

Набор должен версионироваться и использоваться для regression testing.

12.5. Automated Evaluation

По возможности evaluation должна быть автоматизирована и встроена в delivery pipeline.

Изменения следующих компонентов могут требовать повторного evaluation:

  • AI model;
  • system prompt;
  • context;
  • agent instructions;
  • orchestration;
  • tools / MCP;
  • Semantic Layer;
  • business rules;
  • external integrations.

Результаты evaluation должны быть измеримыми и сопоставимыми между версиями решения.

12.6. Load & Stress Testing

Для AI-решений, предполагающих существенную пользовательскую нагрузку, AI-команда определяет и проводит:

  • load testing;
  • stress testing;
  • concurrency testing;
  • endurance testing;
  • rate-limit testing;
  • failure/recovery testing.

Тестируется не только инфраструктура, но и поведение AI-системы при росте нагрузки:

  • изменение latency;
  • рост error rate;
  • деградация AI quality;
  • рост token consumption;
  • рост стоимости;
  • доступность моделей и tools;
  • корректность очередей и retry-механизмов;
  • корректность state management.

12.7. Validation Report

По результатам проверки AI-команда формирует AI Validation Report, содержащий:

  • проверяемый сценарий;
  • версию AI-решения;
  • использованные модели;
  • evaluation dataset;
  • набор тестов;
  • результаты;
  • выявленные ограничения;
  • known issues;
  • performance characteristics;
  • estimated cost;
  • security/governance findings;
  • рекомендации по production;
  • критерии, которые не выполнены.

Результат validation должен позволять принять техническое решение:

Ready for Production Engineering / Requires Changes / Not Ready

При этом AI Validation не заменяет Product Acceptance и стандартное QA тестирование продукта.

12.8. Production Gate

AI-решение не считается готовым к production только на основании положительной клиентской оценки POC.

Перед переходом в production должны быть подтверждены:

  • business acceptance;
  • AI quality;
  • tool/agent correctness;
  • business rule compliance;
  • governance and security;
  • reliability;
  • performance;
  • cost;
  • integration readiness;
  • regression results.

14. Реализация AI Solution

AI-команда самостоятельно реализует AI-часть решения.

В состав реализации входят:

  • agent code;
  • AI services;
  • orchestration;
  • tools;
  • MCP;
  • AI APIs;
  • prompts;
  • context management;

  • evaluation;
  • governance;

AI-код размещается в согласованной архитектуре основного продукта либо в отдельном сервисе, если архитектура требует выделения AI-компонента.

AI-команда отвечает за сопровождение и развитие реализованной AI-части.

15. Интеграция с основным продуктом

AI-команда и основная разработка совместно обеспечивают end-to-end интеграцию.

AI-команда:

  • реализует AI-компоненты;
  • реализует AI-specific integration;
  • интегрирует agents и tools;
  • проверяет API и контракты;
  • проводит end-to-end testing AI-сценария;
  • контролирует соответствие архитектуре.

Основная разработка:

  • реализует необходимые изменения Backend;
  • реализует необходимые изменения Frontend;
  • реализует изменения core product;
  • обеспечивает стабильность существующей продуктовой функциональности.

16. Production Readiness

AI Solution считается готовым к production при выполнении следующих условий:

  • согласована целевая архитектура;
  • определена AI-модель решения;
  • определены границы автономности;
  • определены tools и интеграции;
  • согласован TDR;
  • согласованы требования к Backend;
  • согласованы требования к Frontend;
  • реализованы необходимые изменения core product;
  • реализована AI-часть;
  • актуализирован Semantic Layer;
  • определен Governance;
  • реализован Evaluation;
  • проведено end-to-end тестирование;
  • определены эксплуатационные требования;
  • определены механизмы мониторинга и контроля.

17. Capability Engineering

AI-команда анализирует реализованные решения на предмет выделения переиспользуемых capabilities.

В capability могут быть преобразованы:

  • agents;
  • tools;
  • MCP-интеграции;
  • orchestration patterns;
  • Semantic Layer components;
  • evaluation mechanisms;
  • governance mechanisms;
  • integration patterns;
  • AI services;
  • reusable APIs;
  • product capabilities.

Целью является переход от разработки отдельных AI-функций к формированию набора переиспользуемых AI capabilities компании.

18. Knowledge Loop

AI-команда возвращает накопленные знания в Vibe Coding.

В Vibe Coding передаются:

  • готовые AI-паттерны;
  • reusable components;
  • tools;
  • capabilities;
  • Semantic Layer;
  • ограничения;
  • governance patterns;
  • evaluation patterns;
  • интеграционные паттерны;
  • успешные архитектурные решения;
  • выявленные anti-patterns;
  • lessons learned.

Vibe Coding использует полученные capabilities и знания при создании следующих POC.

Таким образом формируется замкнутый цикл:

POC → AI Engineering → Production → Capability → Knowledge → Vibe Coding → новый POC

20. Ключевая зона ответственности AI-команды

AI-команда отвечает за переход:

от работающего POC

к production-интегрированному AI Solution

и далее к переиспользуемой AI Capability.

Ключевой результат работы команды:

AI Solution, реализованный по согласованной архитектуре, интегрированный с основным продуктом, контролируемый, измеримый и готовый к промышленной эксплуатации.

Основной принцип взаимодействия команд:

Vibe Coding: Validate.
AI Team: Architect, Integrate & Build.
Main Development: Build & Operate Core Product.
