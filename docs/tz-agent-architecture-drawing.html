ТЗ: как описывать и рисовать архитектуру агента

Поле Значение
Дата 07.09.2026
Версия 3.2
Для кого Архитектор или разработчик, которому нужно начертить схему своего сервиса или агента

Образцы нотации ниже вырезаны из двух учебных досок. Рисовать нужно в той же грамматике фигур, не копируя чужие имена продуктов как обязательный деплой.

Правило нотации на всех блоках. Цветная рамка с заголовком задаёт границу ответственности. Внутри узлы: иконка и подпись. Сплошная стрелка это рабочий поток. Пунктир это побочный контур: след, атака, обратная связь. Кружки это ноды пути. Ромб или router это развилка.

Полные доски, откуда взяты кропы:

Зачем этот документ

Схема должна ответить человеку: откуда пришла работа, через какие сервисы она дошла до модели, кто владеет ответом пользователю, где цикл, где побочный эффект, куда пишутся данные, как это потом проверить.

Если у агента нет цикла, это показывают явно: линейный путь, без петли «ради красоты». Если специализаций несколько, сначала решают: это один runtime с навыками или несколько независимых агентов. LangGraph, LangChain, Langfuse и LangSmith на схеме это метки слоя, а не обязательный состав поставки.

User Query

Вопрос блока: кто и чем инициировал работу. Модель сама не «просыпается».

Из чего состоит. Channel это способ входа, не агент и не человек. У канала три свойства: контракт входа (текст, файл, событие), контекст вызова (сессия, тенант), ожидание ответа (вернуть реплику в тот же канал или только поставить работу и уйти). Эти два ожидания нельзя рисовать одной стрелкой.

Какие виды бывают. Диалог ждёт реплику. Поиск часто ждёт карточку или ссылку. Загрузка файла ждёт поля или черновик объекта. Конструктор ждёт сохранённую конфигурацию. Мастер интеграции ждёт опубликованный инструмент. Вызов во внешнюю базу из уже идущей работы это Tool Execution, не User Query.

Что отобразить. Один явный вход на эту схему. Фигура User или Channel, подпись входа, сплошная стрелка request в runtime. Runtime без канала не рисуют.

Пример нотации. Вход это иконка человека и подписанная сплошная стрелка в контур исполнения. Не прячьте запрос внутри «AI-коробки».

Gateway and Application Core

Вопрос блока: кто хранит сессию, кто хранит предметную истину, кто имеет право звать модель. Если всё схлопнуть в «backend», схема это не объясняет.

Из чего состоит. Между человеком и моделью стоят обычные сервисы. Gateway (BFF или API Gateway) принимает вызов канала, видит сессию и тенант, отсекает чужой запрос. OIDC broker рядом: личность уже установлена, агент её не добывает сам. Application Core держит процессы или домен, файлы, поиск, знания. Agent Runtime стоит отдельно: специализации, инструменты, фильтр результата до модели. Снаружи: IdP, LLM, traces, чужая база.

Какие виды бывают. Gateway с сессией у клиента (BFF) или Gateway только с токеном (API Gateway). Application Core как монолит или набор доменных сервисов. Для схемы агента важнее запрет: Gateway не хозяин предметных данных, Application Core не читает чужие таблицы напрямую.

Что отобразить. Минимум четыре разные фигуры: Channel, Gateway, Application Core, Runtime. Пунктиром внешние зависимости. Агент не пишет в операционную базу сам: он отдаёт структурированный результат, запись делает хозяин данных.

Пример нотации. На учебных досках Gateway часто опущен. Его рисуют той же грамматикой, что цветной контейнер LangGraph: рамка, заголовок, вход request слева. Ставят контейнер между фигурой User и контейнером Reasoning Engine / LangGraph. Не сливать User и Planner в один узел.

Auth (OIDC)

Вопрос блока: почему работа идёт от имени этого пользователя, а не «потому что модель так решила».

Из чего состоит. Три слоя, их путают. Authentication: OAuth / OIDC на Gateway. Tenant and session: чужие объекты не видны. Authorization: даже свой пользователь может не иметь права на инструмент или на запись без Human Validation.

Какие виды бывают. Простой контур: вошёл и попал в тенант. Процессный контур: плюс белый список инструментов и флаг «без человека нельзя». Лестницу «чем умнее агент, тем больше можно» не рисуют, пока её нет как продукта.

Что отобразить. Узел или ромб OIDC у Gateway. Секреты внешних систем не в контексте модели. Стрелки «агент → IdP» нет.

Пример нотации. На снимках отдельного OIDC нет. Auth рисуют как узел на входе контейнера, тем же приёмом, что Execution Router: иконка развилки / щита и подпись под ней, сплошная стрелка request проходит через этот узел до Planner.

Agent Pattern

Вопрос блока: сколько runtime и кто отвечает пользователю.

Из чего состоит. База: один агент с инструментами. Инструмент это способность, не второй агент. Второй агент появляется, когда не хватает окна контекста, владельцев способности или контроля задачи.

Какие виды бывают. Навык без смены говорящего: skills / agents-as-tools, диалог остаётся у runtime. Handoff: следующий ответ отдаёт уже другой агент, это должно быть видно. Много исполнителей: coordinator, parallel, swarm. Детерминированная цепочка без LLM-router: код ведёт шаги. Цикл ReAct рисуют кольцом с выходом (схема, лимит кругов, Human Validation, эскалация).

Что отобразить. Одна фраза паттерна на листе. Рядом что отвергли, чтобы не дорисовали swarm или handoff. Несколько фигурок «Agent 1 / 2 / 3» без подписи владельца ответа читать как swarm: так можно только если swarm выбран.

Пример нотации. Учебный снимок показывает контейнер Multi Agent System. Если у вас один runtime, этот ящик не копируют как деплой. Либо подписывают специализации как skills внутри runtime, либо оставляют контейнер и явно пишут «не отдельные процессы».

Pipeline and Nodes

Вопрос блока: из каких шагов складывается одна работа. Agent Pattern говорит, кто владеет ответом. Pipeline говорит, что по дороге происходит.

Из чего состоит. Два семейства узлов. Path (LangGraph): куда дальше, ветка, повтор, стоп. Step (LangChain): prompt, retrieve, tool, model call. Один квадрат «LLM» посередине Pipeline не считается.

Какие виды бывают. Retrieve может кончиться ссылкой без генерации абзаца. Разбор документа: текст, поля, запись. Публикация коннектора: инструмент в реестре, не «ответ чата». Запись состояния процесса это следствие стопа, не шаг модели.

Что отобразить. Имена узлов человеческим языком. Если цикла нет, линейность подписывают.

Пример нотации Path. Кружки-ноды, Execution Router, подпись conditional branch на ребре.

Пример нотации Step. Внутри синей рамки LangChain отдельные иконки: Prompt Builder, Retrieval, Model Call, Tool Execution.

LangGraph · LangChain · LangSmith

Вопрос блока: три разные работы не должны склеиться в квадрат «AI platform».

Из чего состоит. LangGraph (path): узлы, состояние, ветки, цикл, пауза. Он не ищет документы и не пишет след. LangChain (step): как сделан шаг внутри узла. LangSmith / Langfuse (observability): что случилось. Он не выбирает следующий узел.

Какие виды бывают. В контуре называют ту систему следов, которая стоит. Вторая остаётся эталоном слоя. Автопетля «Evaluation сама поменяла prompt в проде» это отдельный вид, его нет по умолчанию.

Что отобразить. Три рамки рядом или вложенность: path содержит step, observability пунктиром с обоих. Сплошные стрелки внутри LangGraph и LangChain. Пунктир в следы: log inputs, log outputs, log invocations.

Пример нотации. Целая учебная доска слоёв: слева LangGraph, в центре LangChain, справа LangSmith, LLM снаружи.

Tool Execution

Вопрос блока: какими руками агент трогает систему. Без блока кажется, что модель «просто знает» данные.

Из чего состоит. Tool это вызов с контрактом: имя, вход, выход, хозяин данных. Internal tools ходят к своим сервисам. External tools к чужим. Протокол вроде MCP удобен, но на схеме важнее граница доступа, не логотип. Tool-result filter стоит между ответом инструмента и следующим шагом Reasoning Engine.

Какие виды бывают. Поиск, чтение файла, запись поля, запрос во внешнюю таблицу это разные tools, не разные агенты, если владелец ответа один. Белый список разный у специализаций. К внешней базе по умолчанию параметризованное чтение. Секрет в вызове, не в prompt.

Что отобразить. Два контура рук лучше одного ящика tools. Filter на ребре «результат → модель». Иконка Tool Execution как на учебном шаге LangChain.

Пример нотации. Узел Tool Execution с иконкой терминала, сплошная связь с нодой path, пунктир в LangSmith log invocations.

Reasoning Engine

Вопрос блока: как агент думает, без облака «brain» на весь лист.

Из чего состоит. Три проверяемых части. Planner: что запросили и какой навык. Tool Execution: вызов инструмента. Conditional Router: повторить, остановиться, спросить человека.

Какие виды бывают. Для навигации по известным объектам план короткий. Для разбора документа цикл естественен. User Query и чистая запись результата этот блок не содержат: думает runtime.

Что отобразить. Три узла с именами внутри одной рамки Reasoning Engine. Кольцо цикла замыкают на Conditional Router, не на LLM напрямую.

Пример нотации. Рамка Reasoning Engine: Planner → Tool Execution → Conditional Router. Вход User Query сплошной. Атака, если есть, красным пунктиром сбоку, не той же стрелкой, что request.

Stress Testing

Вопрос блока: что отсекается до рассуждения. Иначе любая строка выглядит как законный вход в модель.

Из чего состоит. Правила того же Pipeline: тип и размер входа, вреносный файл, повтор одной и той же работы, prompt injection в тексте, запрет превратить модель в автора произвольного запроса к чужой базе. Это не отдельный театр атак.

Какие виды бывают. Файл, короткая строка поиска и диалог требуют разных правил. Контур red team рисуют только если он есть как практика. Иначе достаточно узлов правил на входе Gateway.

Что отобразить. Красная рамка сбоку или узлы на входе Gateway. Связь с Reasoning Engine красным пунктиром и подписью, не сплошным request.

Пример нотации. Заголовок STRESS TESTING, внутри иконки угроз (Biased Opinion, Information Evasion, Prompt Injection), красный пунктир red team attacks в Reasoning Engine.

Human Validation

Вопрос блока: где действие уже нельзя назвать «просто ответом». Запись, создание карточки, публикация наружу это side effect. Без подтверждения его нет.

Из чего состоит. Состояние «нужно решение», причина паузы, продолжение runtime после решения. Несколько ролей Gatekeeper / Auditor / Strategist рисуют только если такой продукт есть. Иначе один контур подтверждения.

Какие виды бывают. Поиск часто без паузы. Извлечение полей часто с правкой спорного. Публикация наружу почти всегда с согласием.

Что отобразить. Паузу на ребре к side effect. Золотая рамка, сплошной вход из Conditional Router, выход в Evaluation или обратно в runtime.

Пример нотации. Учебный контейнер HUMAN VALIDATION с внутренними ролями. Если ролей нет, рамку оставляют, внутри один узел confirmation, без тройки должностей.

Database Layer

Вопрос блока: куда агент ходит за памятью и почему это не одна база.

Из чего состоит. Несколько контуров, даже на одном кластере. Operational DB процесса. Knowledge store для общих имён. Files как байты. Vector Store как сходство. Queues фона. Traces наблюдения. External data только через tool. Secrets это control, не память процесса.

Какие виды ошибки бывают. Vector Store в том же бакете, что байты, без границы. Парсер чужой схемы как истина знаний. Trace наблюдения в тех же таблицах, что поля процесса.

Что отобразить. Цилиндры с хозяином и протоколом. Если движок вектора не выбран, так и пишут.

Пример нотации. Рамка DATABASE LAYER, внутри отдельно Vector Store (кубы) и Relational Database (цилиндр). Двусторонняя связь с исполнением, не «агент читает всё».

Data Processing

Вопрос блока: не склеить подготовку корпуса и исполнение одной работы в одну стрелку «ETL → агент».

Из чего состоит. Corpus ingest: источник → файловый сервис → разбор текста → при необходимости вектор → индекс. Имена сущностей живут в знаниях. Request path: Channel, Gateway, skill, узкий контекст, tools, стоп, запись. Исполнение не переиндексирует весь мир «на лету», если это не его задача.

Какие виды бывают. Простой: текст и поиск по сходству. Сложный: сохранить таблицы и заголовки, навесить описания фрагментов. Сложный рисуют только если он есть.

Что отобразить. Два контура. Снизу Data Processing, сверху request path. Источники отдельной рамкой Data Sources.

Пример нотации. DATA SOURCES (Documents, Code, Spreadsheets, Images) входят в широкую зелёную рамку DATA PROCESSING с тремя стадиями: Re-structuring Data, Structure-aware Chunking, Metadata Creation.

Vector Store and Relational Database

Вопрос блока: какие уровни чтения есть, когда уже тянет нарисовать «всё в Postgres».

Из чего состоит. Relational уровень процесса и relational уровень знаний различны. Vector Store про сходство, не про истину поля. Files про байты. External relational только через tool. Observability про качество работы.

Что отобразить. Легенда уровней. Каждая стрелка чтения заканчивается в одном уровне. Стрелки «агент читает всё» нет.

Пример нотации. Те же два знака, что в Database Layer: кубы Vector Store и цилиндр Relational Database, подписанные по-разному. Не один цилиндр на оба смысла.

Evaluation

Вопрос блока: как узнать, что путь сработал. Без блока архитектура кончается на «вызвали модель».

Из чего состоит. Trace: специализация, tools, попадания поиска, вход и выход, время, стоимость, был ли Human Validation. Дальше метрика по виду пути: находка и ссылка, схема полей, верный навык, стоп по правилу.

Какие виды зрелости бывают. Только trace. Trace плюс эталонные примеры. Плюс LLM Judges. Автопетля правки prompt в проде это отдельное решение, его нет по умолчанию.

Что отобразить. Пунктир с узлов LangGraph и LangChain в LangSmith / Langfuse. Обратная связь в Conditional Router, если петля улучшения принята, тоже пунктиром feedback loop. Observability не ставят третьим оркестратором вместо Reasoning Engine.

Пример нотации Evaluation. Рамка EVALUATION: LLM Judges, Precision & Recall, Latency & Cost. Пунктир назад в Reasoning Engine.

Пример нотации traces. Рамка LangSmith справа: Trace Logger, Output Recorder, Decision Tracker. Только пунктир log inputs / log outputs / log invocations, без сплошного управления путём.

Что должно получиться на листе

С листа без устного комментария видно: User Query, Gateway и Application Core как разные узлы, Agent Pattern и владелец ответа, цикл или его отсутствие, Tool Execution, Human Validation на side effect, Database Layer, Evaluation пунктиром.

Если видны только подписи технологий без этой грамматики рамок, иконок и типов линий, это перечень слов, а не архитектура.
