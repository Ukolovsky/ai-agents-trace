ТЗ. Оргструктура AI-команды (Lead + 3 разработчика)

Модель: команда из 4 человек (Lead + 3 разработчика). Не четыре одинаковых «AI Engineer», а T-shaped команда: общий обязательный фундамент у всех и своя зона глубокой экспертизы у каждого.

1. Lead AI Team: Solution / AI Architect

Главная задача: отвечать за то, что именно строим, как это будет устроено и как оно попадёт в production.

Должен уверенно уметь:

Solution Architecture

  • декомпозировать POC в production solution;
  • выбирать между обычным backend, AI feature, agent, workflow, multi-agent;
  • проектировать end-to-end архитектуру;
  • определять границы AI-компонента и core product.

Agentic Architecture

  • agents / workflows / multi-agent;
  • orchestration;
  • state, memory, planning, reasoning;
  • tool calling;
  • MCP;
  • human-in-the-loop;
  • autonomy boundaries.

Integration Architecture

  • понимать Backend / Frontend / DB / API;
  • формировать TDR;
  • определять, какие изменения нужны core product;
  • договариваться с Backend/Frontend Lead'ами.

Semantic Layer

  • определять бизнес-сущности;
  • relationships;
  • definitions;
  • business rules;
  • capabilities;
  • контракты для AI/tools.

AI Governance

  • permissions;
  • allowed/forbidden actions;
  • approval;
  • escalation;
  • audit;
  • data boundaries;
  • security.

AI Evaluation

  • определять, как доказать, что решение работает;
  • quality criteria;
  • golden datasets;
  • regression;
  • business KPI;
  • tool-use evaluation.

Technology Assessment

  • выбирать модели, фреймворки, MCP, vector/RAG, orchestration и т.д.;
  • проводить benchmark/POC;
  • понимать trade-offs.

Delivery

  • вести решение от POC до production;
  • разбивать работу;
  • принимать архитектурные решения;
  • проводить design review;
  • контролировать техническое качество.

Ключевой критерий: Lead должен быть способен сам спроектировать и объяснить всю систему, даже если код отдельных частей пишут сотрудники.

2. AI Engineer #1: Agentic / AI Engineering

Главная специализация: непосредственно строить AI-систему.

Это самый сильный человек команды именно в агентной логике.

Должен уметь:

  • LLM API;
  • structured output;
  • function/tool calling;
  • agents;
  • workflows;
  • multi-agent;
  • orchestration;
  • state management;
  • memory;
  • reasoning;
  • planning;
  • routing;
  • fallback;
  • model selection;
  • prompt engineering;
  • context engineering;
  • RAG;
  • embeddings;
  • MCP clients/servers;
  • LangGraph / аналогичные frameworks;
  • streaming;
  • async execution.

И главное: не просто написать POC, а сделать production-grade implementation:

User
 ↓
AI Interface
 ↓
Orchestrator
 ↓
Agent
 ↓
Tools / MCP
 ↓
Core Product APIs
 ↓
Business operation

Он должен понимать, где здесь должны быть deterministic workflows, где agentic behavior, где обычный backend.

Production AI code

Он должен уметь писать production AI code, который AI-команда реально отдаёт в production:

  • тесты;
  • error handling;
  • retries;
  • timeout;
  • state persistence;
  • logging;
  • tracing;
  • versioning;
  • configuration;
  • deployment.

3. AI Engineer #2: Integration / Semantic / Backend

Главная специализация: сделать так, чтобы AI действительно понимал и мог использовать продукт.

Это человек на стыке AI ↔ Backend ↔ Domain.

Backend / Integration

Должен хорошо понимать:

  • REST/API;
  • service architecture;
  • DB;
  • transactions;
  • events;
  • queues;
  • authentication/authorization;
  • permissions;
  • API contracts;
  • idempotency;
  • async operations;
  • error handling.

Главное отличие: уметь переводить «агенту нужно уметь создать заказ» в конкретный набор продуктовых возможностей:

AI capability
      ↓
Required business operation
      ↓
API / event / service capability
      ↓
TDR
      ↓
Backend implementation
      ↓
Tool / MCP
      ↓
Agent

Semantic Layer

Здесь он главный владелец Semantic Layer.

Он должен уметь описывать:

  • Business Entity;
  • Entity Definition;
  • Attributes;
  • Relationships;
  • Business Rules;
  • Actions;
  • Capabilities;
  • Permissions;
  • Context;
  • Terminology;
  • Tool contracts.

Например, не просто POST /orders, а понимать: что такое Order в бизнесе, кто может его создавать, какие состояния существуют, какие правила действуют, какие поля обязательны, какие действия допустимы в каждом состоянии.

Результат его работы

AI получает не просто API, а machine-understandable business context.

4. AI Engineer #3: Evaluation / Governance / Production

Главная специализация: сделать так, чтобы AI-решение было надёжным, измеримым и безопасным в production.

Без этой роли команда легко превращается в: «Агент вроде работает, давайте выкатывать».

Evaluation

Должен уметь строить:

  • evaluation datasets;
  • golden sets;
  • test cases;
  • deterministic evaluation;
  • LLM-as-a-judge;
  • trajectory evaluation;
  • tool-use evaluation;
  • regression tests;
  • quality metrics;
  • business KPI;
  • automated evaluation pipelines.

Оценивать не только «правильно ли ответил LLM?», но и «правильно ли агент выполнил бизнес-процесс?»:

Task success
Tool selection
Arguments correctness
Business rule compliance
Final result
Latency
Cost
Safety

Governance / Security

Должен глубоко понимать:

  • authorization;
  • permissions;
  • tool permissions;
  • prompt injection;
  • data leakage;
  • excessive agency;
  • privilege escalation;
  • unsafe actions;
  • human approval;
  • audit;
  • policy enforcement.

И уметь превращать это в технические механизмы:

Agent wants to refund order
        ↓
Policy check
        ↓
Is action allowed?
        ↓
Amount > threshold?
        ↓
Human approval
        ↓
Tool execution
        ↓
Audit

Production AI

Также:

  • observability;
  • tracing;
  • metrics;
  • token/cost monitoring;
  • latency;
  • model failures;
  • retries;
  • fallback;
  • rate limits;
  • caching;
  • model routing;
  • queues;
  • deployment;
  • rollback;
  • incident analysis.

6. Общий фундамент и специализация

Людей не закреплять намертво по принципу «этот только evaluation, этот только backend».

У каждого должны быть:

Обязательный общий фундамент:

LLM → Agent → Tools → MCP → Orchestration → API → Semantic Layer → Evaluation → Governance → Production

А специализация: второй уровень.

Каждый из трёх сотрудников должен быть способен самостоятельно взять относительно небольшой POC и довести его до production. При этом:

  • Engineer 1 быстрее и глубже решит агентную архитектуру;
  • Engineer 2 быстрее и глубже решит интеграцию с продуктом и Semantic Layer;
  • Engineer 3 быстрее и глубже решит evaluation, governance и production reliability.

Lead связывает всё это в единую Solution Architecture.

Тогда команда соответствует заявленной модели:

Vibe Coding → POC → AI Team → Architecture + TDR → AI Build + Core Development → Evaluation/Governance → Production → Reusable Capability.
